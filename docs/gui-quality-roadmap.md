# GUI and code quality roadmap

This page records the original GUI review and the work verified for `v0.0.10-rc.1`. Use emulated devices for behavior tests and desktop previews. Keep model-level profile settings separate from state read from a particular unit and from changes to onboard slots.

| Work | Original finding and approach | Evidence to collect |
| --- | --- | --- |
| Device lifecycle and saves | Stop battery and thumbstick timers when the last unit for a model disappears. Discard late replies to a removed tab. Order GUI writes by model and protect newer edits from older reloads. | Emulated unplug and replug, a delayed battery reply, two rapid edits, a failed first write, a stale settings reply, and pending page edits at unplug and shutdown. |
| Device-first Dashboard | Give device setup priority and remove duplicate module entry points. Distinguish discovery in progress, successful discovery with zero devices, and a failed connection or refresh. Prototype a compact device list and a persistent unit header. Show model, transport, available battery status, and profile scope. | Desktop previews with zero, one, and two units of a model. Emulate service unavailable and recovery, and manually check keyboard traversal, text scaling, and the minimum window size. |
| Refresh and background work | Surface failures from background refresh and review photo-load failure handling. A manual refresh can reload a new or changed device twice. Refresh rebuilds the dashboard collection, and a device reload applies the view model twice when it obtains live state. Reconcile by model and preserve useful selection and focus. Apply stored settings promptly even when the live read is slow. | Count list calls, profile reads, unit reads, and collection changes per action. Test delayed reports, overlapping refreshes, shared-model units, and service errors. Confirm that profile and live-state reads still bring in their respective values. |
| Device view and visual consistency | Extract Health and Lighting from the device view as those pages are redesigned. Use shared typography, spacing, and semantic surface and status styles. Replace font-dependent navigation glyphs with a consistent icon set and preserve visible focus. Review how Lighting, Performance, Power, Scroll, and Calibration load and save. Reuse common behavior where the timing and error semantics agree. | Headless binding tests and before/after desktop comparisons. Verify profile switching, per-key lighting, and unchanged firmware capability and targeting behavior. |
| Rendering and response time | Measure device drawing during hover, selection, and frame painting. Measure startup and page switches with emulated devices. Use the measurements to decide whether to cache stable drawing elements or reduce realized controls. | Repeatable scenarios with before/after frame time, managed allocations, and D-Bus call counts. Verify hit testing, labels, DPI scaling, and accent changes after any optimization. |

## Reliability follow-up

| Area | Implementation and regression coverage |
| --- | --- |
| Editing and saves | Binding drafts identify the original profile, keymap, and layer. The save queue and service revisions protect against stale writes. Emulated tests cover rapid edits, external profile switches, failed saves, explicit reload, and shutdown. |
| Hardware application | A software save reports a separate outcome for each connected unit. Firmware retries check the original endpoint and serial. Onboard mutations require a verified serial. Tests cover rejected acknowledgements, retry, and existing restore rollback. |
| Connection recovery | The daemon reports devices during virtual-input failure and recovers when the user refreshes. The service reconciles control interfaces, expires thumbstick monitors independently of device input, and only polls the receiver for periodic wake recovery. |
| Dashboard and editing | Device cards link affected units to Health. App tabs stay reachable as the device list overflows. Dense editors reflow and per-key lighting has a keyboard-operable list. The desktop smoke test also checks visible Tab focus, single-key capture, draft retention and retry on save failure, and focus return after closing the editor. |

The isolated 150% scale smoke run prints timing and allocation samples for 20 Customize/Lighting page-switch pairs and 20 synchronous drawing renders. Compare runs on the same machine and fixture configuration. The receiver regression records one identity report for an unchanged receiver and zero additional reports for wired and legacy devices.

Research references include [Avalonia's threading model](https://docs.avaloniaui.net/docs/app-development/threading), [accessibility guidance](https://docs.avaloniaui.net/docs/app-development/accessibility) and [performance guidance](https://docs.avaloniaui.net/docs/app-development/performance), and the [.NET tracing tool](https://learn.microsoft.com/dotnet/core/diagnostics/dotnet-trace).
